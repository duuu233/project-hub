## 接口与来源

本轮重新读取 dev 服务 `/api-qianrong/v2/api-docs`。用户组 `SysUserGroupsDTO.groupsSystemMenuDTOList` 的元素仍是 `SysUserGroupsSystemMenuDTO`，包含 `systemId`、`menuList: int64[]`，可以在现有新增/编辑请求保存，无需虚构接口。

| 读取/保存 | 当前使用方式 |
| --- | --- |
| GET `/system/list` | 用户组关联系统候选；按系统ID隔离，不按名称归并 |
| GET `/system/detail?id=…` | 所选系统的 menuIds，沿用系统模块已有响应读取器 |
| GET `/system/menu/list` | 真实菜单名称、层级和停用状态元信息，仅供与系统授权交集，不是用户组全量可授权范围 |
| GET `/user/groups/detail?id=…` | `data.groupsSystemMenuDTOList[].menuList` 回填已选，空数组与缺字段区分 |
| GET `/system/getSystemListByUserGroupsId?userGroupsId=…` | 原系统关联回读，与详情菜单关联核对一致性 |
| POST `/user/groups/add`、`/user/groups/update` | 白名单基础字段 + `groupsSystemMenuDTOList: [{systemId,menuList}]`，不传树、筛选或其它界面状态 |
| GET `/user/groups/menuTreeList` | 角色可选系统/菜单，Swagger说明是登录用户的用户组可选范围，无目标userGroupId查询参数 |

表中路径均带 `/api-qianrong`。本轮没有有效真实会话读取业务响应；系统菜单读取器和用户组详情字段分别依据当前系统实现、此前用户组回填实现及现行DTO，若后台遗漏授权数组，显示错误并停止保存，不默认为全量菜单。没有真实用户组/角色授权写入。

## 用户组交互

- 恢复菜单权限面板，左侧关联系统按ID切换，右侧只显示该系统已授权节点。系统来源的菜单缺失、未知编号、菜单目录异常均不回退全量。
- 新关联系统默认选中其可用菜单；已有用户组只回填保存的menuList，不把系统后来新增的菜单自动授给组。用户切换系统、取消/重新关联时保留各系统本轮勾选；管理弹窗未完成不改实际关联。
- 复用系统菜单树，支持逐项、父子联动、展开折叠、搜索、仅看已选、全选可用菜单及清空。父节点未被系统授权时不擅自补授权，而是把允许节点作为可显示根。
- 新增不能关联停用系统；已关联停用系统保留只读。停用菜单不向新组默认授权，原有停用勾选可回显。
- 至少关联一个系统、每个关联系统至少选一个菜单。无上级授权时提示先配置系统。菜单请求期间/失败禁止提交，支持单系统重试。缺失原授权字段、关联不一致、丢失精度的编号等阻断，不以空列表覆盖。
- 解除关联系统、移除原菜单（包括已被上级撤销的旧权限）保存前确认，取消不写入。详情只读。路由/记录切换丢弃旧响应，不将旧组菜单回填到新组。

## 角色链路核查和修复

- 原角色已经请求menuTreeList，保留该正式来源；不添加文档未支持的目标用户组参数，不新建随意切组接口。系统/page仍用于名称和状态元信息。
- 原systemSources可能从系统元信息的menus回退；现在角色树仅来自menuTreeList，防止越过用户组范围。
- 原collectMenuIds会给孤立根节点自动补parentId，该父节点不一定在上级授权内；已移除这条树外补授权规则，树内祖先仍正常收集。
- 已保存角色超出当前有效用户组树的旧菜单，保存前列出并确认移除，再提交限定范围；取消不保存。空树/系统不可配置时保留本地回显的旧授权，但阻断保存，避免将“查询失败/无可配范围”当成清空或继续越权授权。
- 原角色列字段、用户分配、企业选择、数据范围和本机草稿不变；新授权仍须符合服务端企业和用户组边界。

## 服务端验收边界

menuTreeList是**登录用户用户组**范围，不是按任意目标用户组查询。实际后台需要保证它返回系统与用户组勾选后的有效交集；管理其它企业角色的边界仍须服务端按其归属校验。不能仅靠前端过滤建立鉴权。

上级撤权后，服务端还需在保存和实际访问时重新检查系统∩用户组∩角色，并处理已有角色失效授权及登录菜单/权限缓存刷新。前端能在下一次读取/保存时确认移除，但不等于实时撤销其它已登录账号权限；本轮未改后端或认证缓存。

## 已知问题：编辑时提示「系统授权菜单暂不可读取，已停止配置，请重新加载」（2026-10-26 ssh 排查，未改代码）

- 机制：用户组编辑加载各关联系统时，`systemPermissionScope`（group-menu-model.js）要求 `GET /system/detail` 的 menuIds 全部出现在 `GET /system/menu/list` 中，否则阻断，避免看不见的授权在保存时被静默丢掉。系统编辑页「部分已有权限暂不可读取」是同一类检查。
- 最可能的触发：8b35f23 新增的 `scripts/adjust-qianrong-system-menus.mjs` 把「日志管理」目录下三个日志页移到「系统中心」后**删除该目录菜单**；服务端删除前只校验无子菜单、未分配给角色，不校验系统授权，系统的 menuIds 里仍留着已删除目录的 ID → 菜单列表里查不到 → 阻断。脚本是否已对该环境执行需确认（备份在执行机的 scripts/.backup/，未进 Git）。
- 其它可能：菜单列表若按当前登录用户权限过滤，系统授权多于当前账号可见菜单时同样触发。
- 确认方法：Network 对比出问题系统的 `/system/detail` menuIds 与 `/system/menu/list` 的 menuId，多出的编号查是否为已删除的「日志管理」目录。
- 处理方向（待定）：后端删除菜单时同步清理系统 / 用户组的菜单关联，或一次性清掉悬空 ID；前端可改为「菜单列表确认为全量时，忽略已不存在的编号并提示」，但若菜单列表按用户过滤则会误删真实授权，需先确认接口口径。

仍保留的阻断：系统详情没有返回 menuIds、编号非法或丢失精度、关联系统重复、菜单列表加载失败，以及详情返回了授权但与关联系统不一致。

风险：详情缺授权时按系统全量默认勾选并保存，可能扩大该组的实际授权；页顶提示要求操作人核对。保留的不可读编号如果是已删除的菜单（10-26 排查最可能的原因），会继续随用户组保存；它们原本就已在库里，后端此前接受过。
