# 提单移交仓储的保存后回读

核对日期：2026-10-16。实现入口：`src/views/bill-lading/bill-lading-list/template/handleDetail.vue`。

2026-10-22 feature-v1.8.5 合并确认：保留 1.8.5 的 `detail-body`、AI 侧栏、关联订单 `Order` 及按提单 ID 获取详情洞察的最新接口；同时保留以下移交流程。`keep-alive` 在原布局内部增加 `detailVersion` key，`getDetail` 必须返回有效详情主体，否则移交会误判失败。不能整文件选 master，也不能只选 1.8.5 而丢失回读与子表重建逻辑。

## 调用顺序

仅点击「移交仓储」（`handleSubmit('remove')`）执行：

1. 保留原数据协调、模块校验、提单号重复和清报关不一致确认，调用 `POST /purchase-service/delivery/addOrUpdate`。
2. 保存成功且返回有效提单 ID 后，以**保存结果 ID**调用 `GET /purchase-service/delivery/selectDetail`，不误用新增页不存在或旧路由中的 ID。
3. 详情成功且含 `delivery` 主体后，按现有映射更新基础信息、海运、货物/预警、清报关、检测、结算和编辑权限。回读字段优先，详情映射未包含的客户端展示字段（如币种符号、计重单位文案）保留保存前值。更新 `detailVersion` 重建子表缓存，避免 `isFirstLoad/isDetailLoaded` 阻止本次回显；保留当前标签，不在普通标签切换时重建。
4. 子组件更新后，将详情中的结算金额、重量、成分单价及提单号映射到现有结算展示模型；不再次取价、不拿保存前的金额覆盖最新值。等待 Vue 更新后，继续原有并行的移交仓储、增加付款计划调用。

`GET /delivery/transferStorage` 与 `GET /delivery/addPaymentPlan` 当前都只接收查询参数 `id`（2026-10-16 只读核对开发环境 OpenAPI）。优先使用详情 `delivery.id`，缺失或 null 时沿用保存返回 ID，数值 0 不当成缺失。不擅自将完整详情塞入原 GET 参数，也不变更 API 封装或方法。

## 失败边界与不变行为

- 保存失败或缺少 ID：不读详情、不移交、不生成付款计划。
- 详情失败、网络异常、无数据或缺少 `delivery`：提示获取详情失败，不继续后续调用，不跳成功页；已保存数据不自动回滚。
- 移交或付款计划失败：沿用原失败处理，不成功跳转，页面保留刚回读的数据。
- 普通「保存」不增加详情请求，不触发子表重建或移交；正常编辑/详情初始化仍默认按路由 ID 读取。
- 不修改公共请求层、其它业务模块、原校验规则或并行付款计划语义。

## 验证方式

使用隔离桩件驱动真实 SFC 中的提交、回读与表单映射方法，覆盖新增/编辑、调用顺序、等待回读、最新 ID/缺省 ID/0、普通保存、各阶段失败与取消、页面数据及结算零值、原初始化、空列表，以及 SFC 脚本/模板编译。此验证不等价于真实账号、真实后端写入或完整浏览器交互验收。

验收时需用测试业务数据确认网络顺序为保存→详情→移交/付款，并逐标签检查服务端新 ID、海运/检测/结算值和编辑权限；详情失败时后两请求不得发出。不要用生产数据做无授权移交测试。
